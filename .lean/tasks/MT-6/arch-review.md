## Verdict
FIX. The design is right: one MainActor tracker, protocol-injected dependencies, one apply+process path, generation-guarded async. One defect remains: scheduler registration is frozen at the first tick, so a later change to an account's session key silently turns off its org lists and forced lists.

## Must fix
1. `Claude Usage/Shared/MultiTeam/TeamTracker.swift:222-233` (`syncAccounts`). `TeamPollScheduler.register` does nothing for an id it already knows (TeamPollScheduler.swift:52). An account that gets a session key after its first tick therefore keeps `hasOrgList == false` for the whole app session. Its `dueLists` never include it, and `forceList` always returns false (TeamPollScheduler.swift:89). A 404 on a probe then never brings the list that would confirm the move: it probes 404 every round until the app restarts. The reverse case (key removed) leaves a list due that is never finished.
   Change: add `private var registeredOrgList: [UUID: Bool] = [:]`. In `syncAccounts`, compute `let has = credentials.sessionKey(for: p) != nil`. If `registeredOrgList[p.id]` exists and differs from `has`, call `scheduler.unregister(accountId: p.id)` first. Then call `scheduler.register(..., hasOrgList: has, ...)` and set `registeredOrgList[p.id] = has`. In the unregister loop, also remove the id from `registeredOrgList`. Delete the `ponytail:` comment. Add a test: a profile with no session key ticks once, then gets a key, then a probe 404 leads to a forced list on the next round.

## Notes
- AC13 (stop during a round). Probe results are dropped at the gen check (line 359) and after each account (line 398). But if `stop()` lands during a group-move or forced-list await inside the round, the accounts already applied stay written, and their events stay in the in-memory `global`. The next `persistGlobal` (for example from `makeCurrent`) saves those events. Each account's write is a complete, valid state, so this is acceptable. The tester should stop during the probe fetch, as the walkthrough's test does.
- Request budget. The background forced-list Task in `ingestLive` (lines 165-169) is outside `isTicking`. It can overlap a tick's lists or probes for the same account, so up to 2 requests run at once for that account against the spec's cap of 1. State stays consistent: everything runs on the MainActor and each apply re-reads state at the time it runs. Possible later change: let `scheduler.forceList` mark the list due and let the next tick run it, with no Task. The packet asked for a Task, so this is not a must-fix.
- `tick` returns early when no profiles are left (line 213), after `syncAccounts` but before `repairCurrent`. A `global.current` that points at a deleted last profile then stays persisted. It is harmless: `liveTarget` returns nil, and the next profile repairs it.
- Each `process`/`detect` call goes through `ProfileManager.updateOrgTracking`, which rewrites the whole profiles file. That is about 2N writes per round, fine for N ≤ 5. MT-7 should check that observers of `profiles` do not start a refresh on each write.
- Contract matches spec §10. Adapters do no Keychain reads, and fingerprints are not logged. Invariant 3 holds: `followedOrgId` is set only when the followed org changes (AccountRules.swift:43,130), and live success never saves `claudeUsage`. Group-move peers are limited to session-key accounts, which matches spec §6 step 1. The extra init parameters (`isEnabled`, `runsLoop`) have defaults, so `shared` and the contract are unchanged.
